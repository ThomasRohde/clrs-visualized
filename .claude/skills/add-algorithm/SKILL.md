---

Add a new algorithm to the site. Follow these steps in order — the two-registry step is the one most likely to be missed.

## 1. Write the recorder

Create `src/algorithms/<area>/<name>.ts` (kebab-case filename, e.g. `sorting/bubble-sort.ts`). Model it on an existing recorder in the same area (e.g. `src/algorithms/sorting/insertion-sort.ts`) rather than starting from scratch — match its shape exactly:

- Import `createRecorder`, `type AlgorithmModule`, `type Trace` from `../types.ts` (relative import, `.ts` extension required — see CLAUDE.md).
- Represent the input as 1-indexed: `const A: Array<number | null> = [null, ...input];`. All algorithms in this codebase do this to mirror CLRS's pseudocode numbering.
- Write `export function record(input: number[]): Trace` that runs the algorithm and calls `emit(proc, line, array, hi, note)` from `createRecorder()` at every meaningful step (each comparison, swap, write, and loop-variable update — enough that scrubbing through steps tells the whole story). Increment `stats.comparisons` / `stats.swaps` / `stats.writes` right before emitting the step that reflects the change.
- `proc` must match a key in the `procedures` map below, and `line` is the 1-based pseudocode line being executed.
- `hi` (highlight) is a free-form object, but **`rolesForStep()` in `src/visualizers/array-bars.ts` is the authority on which keys mean anything** — read it before inventing a key. It maps `sortedUpTo`/`sortedFrom`/`heapSize`/`doneSet`/`settled`/`placed`/`done` to settled elements, `compare`/`l`/`r`/`reading`/`source` to reads, `pivot`/`key`/`marks` to marked elements, and `shift`/`writing`/`swap` to a mutation; `range` draws the owning-subarray bracket, and `aux` feeds the auxiliary strip. Use `doneSet` (an explicit index list) when what has settled is neither a prefix nor a suffix — counting and radix sort fill their output out of order. Use `marks` when more than one element is marked at once. A key not listed there is silently ignored — the bar just stays in the default colour, with no error, which is how merge sort emitted `source` for months without it highlighting anything. Reuse these rather than inventing new ones unless the renderer genuinely needs to show something new.
  - **For a `cells` algorithm the authority is `rolesForCells()` in `src/visualizers/cells.ts` instead**, and its keys name **cell ids**, never positions — a list splices, so the third box stops being the third element. It reads `look` / `move` (or `writing`) / `mark` / `done`, plus `scope` (an id list, drawn as a bracket over the run that is currently _inside_ the structure), `scopeLabel`, and `pointers` — a `{ label: cellId }` map that draws the variable names above the cells, so a cells algorithm needs no equivalent of `markersFor`. Two variables naming the same cell stack rather than overprint. The step carries `CellsData` as its snapshot rather than an array: `emit(proc, line, { kind: 'cells', rows: [...] }, hi, note)`.
  - **Pointers between cells** are `Cell.next` and `Cell.prev`, drawn as arcs in a labelled lane under the row — one lane per field the snapshot actually uses, so a structure with no pointers is laid out as it was before arcs existed. `null` means NIL and draws a terminator; **`undefined` means no such pointer and draws nothing**, which is how a freshly allocated object shows as unlinked and how a spliced-out one stops showing the stale pointers it still holds. An arc takes a role colour like a cell does, through `hi.links` — a `{ 'x3.next': 'move' }` map keyed the way the book writes the field. Use it wherever the pointer assignment _is_ the step, as it is in every line of `LIST-PREPEND`: there is no cell to colour instead. `rolesForLinks()` is the authority, and `tests/legends.test.ts` counts what it returns, so a key that mentions only the boxes will fail.
  - **Keep the row a fixed length for the whole run.** The renderer sizes cells to the widest row of the step it is drawing, so a row that grows rescales every cell mid-trace and the reader reads the rescaling as something the algorithm did. Reserve the slots an operation will need and draw them empty — `value: null` is a dashed outline.
  - **`scope` brackets the _first_ row.** Its caption is drawn in the gap above the row it marks, and only the first row has a band reserved for one; above any other row the caption is drawn across the cells above it, and a screenshot taken on a step with no scope will not show it. If the row that deserves the bracket is not the input row, put it first — chapter 26's parallel merge puts the output `A` above the input `T` for exactly this reason.
  - **More than one row means one shared column grid**, which is what lines a hash table's chains up under their buckets. Three things are row-local, and ignoring that produces a picture that lies rather than an error: an **arc** can only reach a cell in the row that holds the pointer; the **scope bracket** takes its top from the topmost cell it names, so bracket one row at a time; and **`pointers` markers** hang above the _first_ row on a leader line, so a many-row structure should not use them at all. Vertical room is the binding constraint — the canvas is 190px at the narrow breakpoint — so a five-row structure has no height for arc lanes, and its rows have to carry their order by adjacency, with the prose saying so.
  - **For a `tree` algorithm the authority is `rolesForTree()` / `rolesForEdges()` in `src/visualizers/tree.ts`.** Keys name node ids: `look` / `move` (or `writing`) / `mark` / `done`, plus `scope` (an id list, drawn as a hull round a subtree), `scopeLabel`, `pointers`, and `edges` — a `{ 'n1>n2': 'look' }` map, because following a pointer often _is_ the step and there is no node to colour instead. A `null` child slot consumes a column, which is how a lean stays visible and how NIL squares are turned on: declare `[null, null]` to draw them, omit `children` to draw nothing.
  - **For a `graph` algorithm the authority is `rolesForGraph()` / `rolesForGraphEdges()` in `src/visualizers/graph.ts`.** Same keys, naming vertex ids, plus `edges` keyed `'from>to'` (either orientation resolves on an undirected graph) and `scope` — which here is a **ring round each named vertex**, not a hull, since the members of a set in a graph are rarely adjacent. **The recorder owns the layout**: build the input through `src/algorithms/graphs/graph-input.ts`, which supplies the generators, the edge-list parser and the normalized positions, and never let a position change between steps — a vertex that drifts destroys the reader's tracking of where the search has got to. Verify a graph algorithm against a **theorem**, not a re-run: `src/algorithms/graphs/graph-check.ts` holds the shortest-path, MST, max-flow and matching characterizations.
  - **For a `grid` algorithm the authority is `rolesForGrid()` / `rolesForArrows()` in `src/visualizers/grid.ts`.** Cells are named `"row,col"`. Same role keys, plus `scope` — a **rectangle** round the bounding box of the named cells, since the interesting subsets of a table are contiguous — and `arrows`, a list of `{ from, to, role? }` that draws "this entry came from that one". Arrows are how a dynamic program says what it is; reconstructing the answer at the end is a walk along them, and without them the walk is invisible. A cell carries a `value` and a `note` (the corner mark: a split point, a back-pointer, a next state) and the note is deliberately not a second colour. **Emit the table at final size from the first frame**, unfilled entries as `null` — a table that grows rescales every cell mid-run and the reader reads the rescaling as something the algorithm did.
  - **For a `plot` algorithm the authority is `rolesForPlot()` / `rolesForPlotLines()` in `src/visualizers/plot.ts`.** Points carry `x`/`y` in the data's own units, `anchor: true` for something the algorithm _placed_ rather than was given, and `attrs` for E6 badges. `series` are polylines (a function's curve, a running total, a trail), `links` join two points by id, and both take roles through `hi.series` / `hi.links`. **The recorder owns `xRange` and `yRange` and they are fixed for the whole trace** — axes refitted per frame would move every point as the algorithm ran, which is the graph-layout rule again and matters more here. A link is usually the _cost_: k-means' spokes squared are its objective function.
  - `markersFor()` in the same file is a **separate** switch on `step.proc` that draws the variable-name labels (`i`, `j`, `p`, `r`). A new procedure needs a case there or it gets no markers. Take care with an algorithm whose chart changes which array it shows mid-run: a marker keyed to the input array names the wrong bar once the chart has moved to an output array.
- `note` is a short plain-English sentence describing what just happened — written for a reader stepping through one step at a time.
- Return `{ steps, finalArray: A.slice(1) as number[] }`. `finalArray` is **optional**: a structure algorithm with no array to leave omits it, and then its `result.kind` must be `transforms` with a `verify` carrying the whole claim.
- Export `export const <camelCaseName>: AlgorithmModule = { id, name, visualizer, procOrder, procedures, complexity, record }`:
  - `id`: kebab-case, stable, referenced from chapter frontmatter (e.g. `'bubble-sort'`).
  - `name`: display name (e.g. `'Bubble Sort'`).
  - `visualizer`: **all six exist.** `'array-bars'` for array/sorting algorithms, `'cells'` for slot-and-pointer structures (stacks, queues, lists, hash chains), `'tree'` for anything rooted (search trees, B-trees, forests — nodes are boxes sized to their keys), `'graph'` for Part VI, `'grid'` for tables and matrices, `'plot'` for continuous data. Pick by what the reader has to _see_: a grid when the interesting thing is which already-filled cells the current one is computed from, a plot when it is a distance or a slope rather than a comparison.
  - `result`: **required unless the algorithm sorts.** A `ResultContract` of `{ kind, verify? }` telling the test suite what a correct run produces — `'sorts'` (the default), `'permutes'`, `'preserves'` (the array is left untouched), or `'transforms'` (no structural claim at all, and then `verify` is mandatory). `verify(input, trace)` returns a complaint string or `null`. Anything the algorithm _returned_ that is not the array goes in `Trace.output` as a `Record<string, number>` for `verify` to check — the order statistic, the number of hires, the final heap size.
  - `aux` (optional): rows of chips above the chart, for values that live outside the array — merge sort's `L` and `R`, insertion sort's `key`, counting sort's `C`. Each row is `{ key, label, hint? }`, and a step fills it with `hi.aux[key] = auxOf(values, ptr, labels)`. `values` is 1-indexed like `Step.array`; `labels` captions the chips, which is what makes an array indexed by _key_ rather than by position readable. Always snapshot through `auxOf` — `emit` copies `array` but stores `hi` by reference, so a live buffer would show every earlier step its final contents. A declared row that no step ever fills is a test failure.
  - **If the input is not a list of numbers**, widen `AlgorithmInput` in `types.ts` and add a narrowing predicate beside `isGraphInput` / `isTextInput`. This has been done twice and cost one line each time: `record`, `verify` and the `InputSpec` hooks are declared as **methods**, so TypeScript compares their parameters bivariantly and every existing array-shaped module keeps compiling untouched. Encode anything that _can_ be a number list as one instead — chapter 35's set cover packs a family of sets into `[n, ...bitmasks]` and parses `1,2,3; 3,4` into it.
  - `input` (optional): an `InputSpec` of `{ min, max, placeholder, note }` controlling what the player generates and what it accepts from the reader. For an input that is not a list of values at all — a count of operations, a graph — supply `generate`/`parse`/`size` instead: they replace the numeric reader outright, and `size` is what keeps the `n` readout honest (the binary counter's input is `[n]`, meaning _increment this many times_). Defaults to 5‥78. Set it when the algorithm only makes sense on particular keys — counting sort uses `0‥9` so its count array stays short, radix sort `100‥999` so `d = 3`.
  - `procedures`: one entry per named procedure, each with `title` (signature line), `lines` (body, no line numbers), `indent` (nesting depth per line, same length as `lines`) — transcribe from the book.
  - `procOrder`: procedure names in display order.
  - `complexity`: `{ best, average, worst, space }` as strings (e.g. `'Θ(n log n)'`). `stable` and `inPlace` are optional — omit them rather than inventing an answer where the question is meaningless, as it is for `RANDOMIZED-SELECT` or a priority queue, and the card drops the row. `extra` takes `[term, value]` rows appended after the standard ones, and is usually where the fact that actually matters lives: `['Expected hires', 'Hₙ ≈ ln n + 0.577']`, `['Assumes', 'integer keys in 0‥k']`.

## 2. Register in both places

This project keeps two separate registries in sync by hand — **both must be updated**:

- `src/algorithms/registry.ts`: import the module and add it to the `ALGORITHMS` array.
- `src/algorithms/lazy.ts`: add an entry to `ALGORITHM_LOADERS` keyed by the algorithm's `id`, e.g.:
  ```ts
  'bubble-sort': () => import('./sorting/bubble-sort.js').then((m) => m.bubbleSort),
  ```
  Note the import path uses a **`.js` extension**, not `.ts` — this is a dynamic import resolved by Vite at build time, unlike the static `.ts`-suffixed imports used everywhere else in this codebase.

## 3. Give it a legend

`src/visualizers/roles.ts` maps the six coded colours to what they mean **in a given algorithm**, and the on-screen key above the visualization is generated from it. Add an entry to `LEGENDS` keyed by the algorithm's `id`:

```ts
'bubble-sort': [
  ['look', 'compared with its neighbour'],
  ['move', 'swapping'],
  ['done', 'bubbled to the top'],
],
```

Two rules:

- Write what the colour means **in this algorithm** ("the key looking for its slot"), not what the role is called ("marked element"). The generic phrasing is what `DEFAULT_LEGEND` already gives you, and `tests/legends.test.ts` rejects a legend entry that reuses one of its four wordings verbatim.
- **List every coded colour that appears on the chart, and nothing else** — and word it for what the colour actually marks. On the cells renderer, membership of the structure is the _bracket_, not the fill, so a cell inside a stack is painted `rest` exactly like one outside it: a `rest` entry reading "outside the stack" would be a lie the test cannot catch. That covers chart chrome as well as bar fills: the subarray bracket and the heap boundary line are drawn in the scope colour, so they earn a `scope` entry — worded to say which mark the reader is looking for (`['scope', 'the heap boundary line']`), since there is no coloured bar to find.

Both directions are enforced. `tests/legends.test.ts` runs `rolesForStep` (or `rolesForCells` / `rolesForTree` / `rolesForGraph` / `rolesForGrid` / `rolesForPlot` and their edge, arrow and line counterparts, per the module's renderer) over real traces and fails if the key promises a colour no step produces, or if a step produces a colour the key never mentions. Skipping the `LEGENDS` entry altogether is also a failure — falling back to `DEFAULT_LEGEND` is a wasted teaching opportunity, not a shortcut.

## 4. Wire it into a chapter

Reference the new `id` from a chapter's frontmatter `algorithms: [...]` array and embed it with `<AlgorithmPlayer id="..." />` (see the `add-chapter` skill, or edit an existing chapter directly). The build fails with a clear error if a chapter references an unregistered id, and `content.config.ts`'s schema is what enforces it.

## 5. Verify

- `npm test` — `tests/algorithms.test.ts` generatively tests every entry in `ALGORITHMS`: correctness against the module's own `result` contract on random/sorted/reversed/edge-case inputs, well-formed steps, non-decreasing counters, complete metadata, that every declared aux row gets filled, and that `finalArray` matches the last step. `tests/legends.test.ts` checks the key against what the renderer paints. Adding the algorithm to the registry is what makes it get covered — no new test code is needed for the algorithm itself.
- `npm run check` — Astro/TS diagnostics.
- `npm run verify:players -- --only <id>` — steps the new player through every step in a real browser, in both themes at three widths, and fails on console errors, a player that never boots, a blank canvas, missing narration or pseudocode highlight, and panel height shifting mid-trace. It starts its own dev server. Add `--shots` and **look at the images**: the one thing it cannot check is whether each variable marker sits over the bar it names, and a marker keyed to the input array will point confidently at the wrong bar on any step where the chart has moved to an output array.
